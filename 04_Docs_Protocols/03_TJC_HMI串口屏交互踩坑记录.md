# 淘晶驰（TJC）串口屏与STM32通信踩坑记录

## 背景

项目使用淘晶驰TJC串口屏通过USART1（9600bps）与STM32F103通信，实现：
- 按钮切换状态机
- 输入框发送目标距离/编号给STM32
- STM32发送测量结果到屏幕显示

---

## 坑1：状态切换字节与TJC返回包冲突

### 问题描述

最初设计用单字节 `0x01~0x14` 作为状态切换指令，TJC屏按钮事件写：
```
printh 03
```

STM32中断里判断：
```c
if (res >= 0x01 && res <= 0x14) {
    // 切换状态
}
```

**现象：** 状态切换正常，但紧接着发送距离数据时，`target_D` 不更新。

### 根因

TJC屏执行完 `printh 03` 后，**会自动发送指令执行成功的返回包**：
```
0x01 0xFF 0xFF 0xFF
```

其中 `0x01` 落在 `0x01~0x14` 范围内，触发了状态切换处理，同时清零了 `UART_RxCounter`。导致紧接着发来的距离数据被丢弃。

### 解决方案

在 `App_Init` 里发送 `bkcmd=0` 关闭TJC返回包：
```c
printf("bkcmd=0");
putchar(0xFF); putchar(0xFF); putchar(0xFF);
```

> **注意：** `bkcmd=0` 需要在STM32上电后发送，TJC屏断电重启后会恢复默认值（有返回包）。如果不想每次上电都发，可以在TJC屏工程的初始化页面里写 `bkcmd=0`。

## 坑2：`D=xxx\n` 文本协议解析失败

### 问题描述

START按钮事件：
```
print "D="
prints t_in.txt,0
printh 0D 0A
```

STM32收到 `D=130\r\n`，中断里用 `strncmp` 解析，但 `target_D` 始终为0。

### 调试过程

1. 调试器显示 `UART_RxBuf` 内容正确（`D=130\0`）
2. 但 `Command_Parser` 执行时 `UART_DataReady=0`，直接 return
3. 原因：`UART_DataReady` 标志位存在竞争——`\r` 置1后，主循环在 `\n` 到来之前已经执行了 `Command_Parser` 并清零

### 解决方案（中间方案，后被替换）

将解析逻辑从主循环移入中断，`\r/\n` 到来时直接解析赋值，消除标志位竞争。

## 坑3：`prints` 指令后的字节干扰

### 问题描述

改用包头协议后：
```
printh AA
prints t_in.txt,0
printh 0D 0A
```

调试显示收到 `AA 35 0D 0A`，数据正确，但解析仍然不触发。

### 根因

`printh 0D 0A` 发出 `\r`（`0x0D`）和 `\n`（`0x0A`）两个字节：

1. `\r` 到来 → 触发解析条件，执行 `atoi`，`UART_RxCounter=0`，`s_frame_type=0` ✅
2. `\n` 紧接着到来 → `UART_RxCounter=0`，条件 `UART_RxCounter > 0` 不满足

**但实际上 `\r` 那次应该成功了**，问题是调试器单步时中断被挂起，看不到 `\r` 那次的执行，误以为没有解析。

真正导致"需要点两次"的原因是：**OLED 200ms 定时刷新**，第一次点击数据已经正确了，但要等最多200ms才显示出来，用户以为没反应就点了第二次。

## 坑4：需要点两次才能看到OLED更新

### 问题描述

第一次点击START，`target_D` 已经被正确赋值，但OLED没有立刻更新，要等200ms。

### 根本原因

当时协议只有包头没有包尾（`printh AA` + `prints t_in.txt,0`，没有结尾符），解析逻辑是"收到下一个包头时触发上一帧解析"：

- 第一次点击：发 `AA 37`，数据存入缓冲区，**但没有触发解析**（没有包尾，也没有下一个包头）
- 第二次点击：发 `AA 37`，收到新的 `AA` 包头，触发**上一帧**的解析，`target_D` 才被赋值

所以本质是**缺少包尾导致解析延迟一帧**，不是OLED刷新延迟的问题。

### 解决方案

加入 `0xCC` 作为包尾，每帧格式完整：`[AA/BB] [数字字节...] [CC]`，收到 `CC` 立刻解析，一次点击即生效。

## 最终协议设计

### 问题

`printh 0D 0A` 发出的 `\r\n` 两个字节，`\r` 触发解析后 `UART_RxCounter` 清零，`\n` 到来时条件不满足，逻辑上有歧义。

### 最终方案：明确的包头+结尾符

| 字节 | 含义 |
|------|------|
| `0xAA` | 距离帧包头，后面跟距离数字 |
| `0xBB` | 编号帧包头，后面跟编号数字 |
| `0xCC` | 帧结尾，触发解析 |
| `0x00` | 强制复位到 STATE_IDLE |
| `0x01~0x14` | 状态切换单字节指令 |

**TJC屏按钮事件写法：**

距离输入（START按钮）：
```
printh AA
prints t_in.txt,0
printh CC
```

编号输入：
```
printh BB
prints t_in.txt,0
printh CC
```

状态切换（各模式按钮）：
```
printh 03    ← 基础3与4，其他类推
```

**优点：**
- 包头明确标识数据类型，不需要解析字符串前缀
- 结尾符 `0xCC` 不会和任何TJC系统字节冲突
- `\r`、`\n`、`0xFF` 全部忽略，不影响解析
- 一次点击立刻生效，OLED即时更新

## 经验总结

1. **TJC/Nextion屏有自动返回包**，默认开启，会干扰STM32接收。上电后发 `bkcmd=0` 关闭，或在屏的初始化页面里写。

2. **包头包尾必须成对**，只有包头没有包尾时，解析依赖"下一个包头触发上一帧"，导致每次操作都延迟一帧才生效，表现为"需要点两次"。用明确的单字节包尾（如 `0xCC`）让每帧自己完整，一次点击立刻生效。

3. **不要用 `\r\n` 作为结尾符**，因为这是两个字节，第一个字节处理完后状态已经改变，第二个字节到来时条件不满足，容易出问题。用单个明确的字节（如 `0xCC`）作为结尾更可靠。

3. **不要用 `D=xxx` 这种文本前缀协议**，`D`、`=` 这些字符的ASCII值可能和控制字节冲突，解析也依赖 `strncmp`，容易出问题。用包头字节直接标识数据类型更简单。

4. **标志位竞争**：中断置标志，主循环清标志，如果主循环跑得快，标志可能在下一个字节到来之前就被清掉。解析逻辑尽量放在中断里直接完成，不要依赖标志位传递。

5. **OLED定时刷新延迟**：如果数据更新后需要立刻反映到显示，加一个"立即刷新"标志，不要只依赖定时刷新。
